判断是否在docker容器中

靶场环境：https://hexc2.com/

方法一：检查 /.dockerenv 文件

Docker 默认会在容器根目录创建该文件。运行 ls -la /.dockerenv 或 test -e /.dockerenv && echo “In Docker”，若存在通常说明在 Docker 中（部分定制镜像可能删除此文件）。

方法二：查看 /proc/1/cgroup

运行 cat /proc/1/cgroup（或 grep -i docker /proc/1/cgroup），如果输出包含 docker、containerd 或 kubepods，通常表示在容器或 Kubernetes 环境中。注意：在较新的 cgroup v2 系统中，该文件内容可能为空或结构不同，需结合其他方法。

方法三：观察进程列表与 PID 1

运行 ps -ef 或 ps aux。容器内的进程数量通常很少，且 PID 1 往往是应用启动命令或精简 init 进程（如 sh、python、node），而不是宿主机常见的 systemd。

方法四：查看环境变量与挂载信息

运行 env 检查是否存在容器注入的环境变量；运行 df -h 或 mount 查看根文件系统是否映射自 overlay/容器存储驱动。

类型一：特权容器

容器以 –privileged 启动。挂载宿主的虚拟磁盘，读取里面的 flag。
场景
你通过某个入口拿到了一个容器内的 root shell。

先看看这个容器有什么特别的地方：设备、能力、挂载点。

目标
逃逸到这台「宿主机」，读取 /root/flag。

提示
ls /dev/ 看看有什么不该出现在容器里的东西。
信息收集，执行

正常容器的 /dev 里只有 null、zero、random 这类设备。vda 是虚拟磁盘，它出现在容器里，说明宿主块设备已经被暴露进来。看到它就可以直接挂载：

命令解释：

  1. mkdir -p /mnt/host
  • mkdir：创建目录
  • -p：递归创建父目录；目录已存在也不会报错
  • 作用：准备挂载点 /mnt/host
  1. mount /dev/vda /mnt/host
  • mount：挂载块设备
  • /dev/vda：虚拟化环境（KVM）里的第一块虚拟磁盘（virtio 盘）
  • /mnt/host：挂载点，挂载后磁盘内容就出现在这个目录下

⚠️ 前提：/dev/vda 内有可识别文件系统（ext4/xfs 等）；如果是裸盘没格式化会挂载失败

  1. echo MOUNT_OK
  • 前面两步都成功后，打印字符串 MOUNT_OK，用来做脚本里的成功标记

最终读取到flag如图：


mount 需要 CAP_SYS_ADMIN，而 –privileged 把全部 capability 都给了容器，同时关掉 seccomp 和 AppArmor。设备侧也一样：默认的 device cgroup 不允许容器看到宿主磁盘，–privileged 把这个限制一起放开。如果 /dev 里没有 vda，不要马上放弃，设备名也可能是 sda、nvme0n1。先看 cat /proc/partitions 或 lsblk，只要能列出宿主磁盘，就说明设备隔离已经失效。修复时不要只盯着 –privileged，还要检查有没有 –device /dev/vda 这类写法。需要挂载能力就单独给 CAP_SYS_ADMIN，保留 seccomp 和 AppArmor，不要把宿主块设备交给容器。

类型二：Socket 泄露

容器挂载了宿主 docker.sock，用它起一个新容器挂宿主根即可读到 flag。

场景
你在一个容器里。ls -la /var/run/ 会看到一个不该出现的东西。

目标
通过它读到宿主机的 /root/flag。

信息收集

权限位开头的 s 表示 socket 文件。接着用它列容器：

挂载宿主机根目录，并cat flag

这条命令里，-v /:/host 冒号左边的 / 是宿主路径，由宿主 Docker 解析。新容器只是执行 cat，真正越界的是 Docker daemon。Docker API 本身没有细粒度权限，能连上 socket 基本等于能做宿主 root 能做的事。如果容器里没有 docker 客户端，实战中可以上传一个静态编译的 docker，或者用 curl –unix-socket /var/run/docker.sock 直接调 API。判据仍然是 ps 能不能看到宿主容器。修复：业务容器不要挂 /var/run/docker.sock。需要管理接口就用 docker-socket-proxy，只开放只读接口；需要构建镜像就用 Kaniko 或 BuildKit，不要为了图方便把 socket 塞进容器。

类型三：宿主 PID 命名空间

容器共享宿主 PID 命名空间，能直接看到并进入宿主进程的根文件系统。

场景
ps aux 的输出里，PID 1 不是容器自己的 init。

目标
读到宿主的 /root/flag。
信息收集

容器自己的 PID 1 应该是 /bin/sh 或业务入口进程。这里出现 /sbin/init 和 [kthreadd] 这类内核线程，说明容器和宿主共用了 PID namespace。

继续看 /proc/1/root：

/proc/<pid>/root 指向该进程看到的根目录。PID 1 是宿主 init，它的根就是宿主根，所以这个符号链接直接绕过了容器自己的文件系统视图。

路径不要写错：/proc/1/root/root/flag 里，第一个 root 是 proc 链接，第二个才是宿主的 /root 目录。如果 ps 看不到宿主进程，先确认不是 --pid=container:<name>；共享单个容器的 PID namespace 危害小一些，但同样会泄露该容器的进程。

修复：不要使用 --pid=host。需要看宿主进程指标，用 cAdvisor、node_exporter 这类组件，不要把宿主进程表直接暴露给业务容器。

类型四：能力位放大

容器挂了宿主的敏感目录，还带着 CAP_DAC_READ_SEARCH —— 路径权限形同虚设。
场景
ls -ld /hostroot 是 700，但你是 root。

目标
读到 /hostroot/flag。

信息收集，先看目录权限和 capability：

/hostroot 是 700，里面的 flag 是 600。按普通 DAC 规则，这个目录进不去、文件也读不了。但 CapEff 是 a80425fb，把它拆开看，bit 1 是 CAP_DAC_OVERRIDE，bit 2 是 CAP_DAC_READ_SEARCH；这个值包含前者，不包含后者。也就是说，容器里的 root 仍然保留了 DAC_OVERRIDE，读 700 目录不会被拦。

这一类配置通常被归到 CAP_DAC_READ_SEARCH 名下。严格说，DAC_READ_SEARCH 只绕过读和目录遍历，DAC_OVERRIDE 读写都能绕；两者都能让 700 目录失效，区别在于能不能改文件。复现时以 CapEff 为准，不要只背名字，可以用 capsh --decode=00000000a80425fb 展开确认。

修复：不要挂宿主 /root、/etc、/var/lib/docker 这类目录；必须挂就加 :ro，并尽量只挂单个文件。不要给 CAP_DAC_READ_SEARCH，也不要用 CAP_DAC_OVERRIDE 代替。

检查项 要处理的值
